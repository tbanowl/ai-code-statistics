## 1. 背景与目标

Git-AI Code Metrics 用于采集、存储和分析 Git 仓库中的 AI 代码归因数据。系统由两部分协同工作：

1. `git-ai` 客户端：Rust 实现的 Git 扩展。它通过 Git 代理、Agent checkpoint、Git hooks 和 Git Notes 记录 AI 代码归因。
2. Python 后端：Flask 服务。它接收 `git-ai` 上传的 metrics、CAS 对象、authorship notes 和 OAuth 请求，并通过定时任务生成统计数据。

本设计文档描述两个项目：

- Python 统计平台的后端技术设计。
- `git-ai` Rust 客户端项目的技术设计。
- 两者之间的 API、数据、认证和同步边界。

文档不描述 frontend。

### 1.1 设计目标

- 接收 `git-ai` 客户端上传的 metrics 事件和 authorship notes。
- 将原始事件异步解析为结构化事件表，支持失败隔离与重试。
- 维护仓库、分支、贡献者等统计维度。
- 基于 committed events 生成每日聚合统计。
- 基于 Git blame 与 authorship notes 计算仓库当前代码的 AI 归因占比。
- 支持 Codeup merge webhook 后的 authorship notes 补偿和重算。
- 提供 Worker API、统计 API、调度 API 和运维 API。
- 支持 MySQL/PostgreSQL/SQLite 形态下的 SQLAlchemy ORM 访问。
- 描述 `git-ai` 的 Git 代理、checkpoint、authorship log、历史改写、daemon、metrics 和远端同步设计。

### 1.2 非目标

- 不设计或描述前端页面、组件、交互和构建产物。
- 不替代 `git-ai` 的 Git AI Standard；后端只按标准消费和存储 authorship log。
- 不在后端推断 AI 代码。AI 归因必须来自 `git-ai` 的 checkpoint、metrics 或 authorship notes。
- 不要求后端直接修改业务仓库提交历史。

## 5. `git-ai` 项目技术设计

### 5.1 项目定位

`git-ai` 是 Rust 实现的 Git 扩展，核心目标是在不改变开发者 Git 工作流、不修改提交历史的前提下，把 AI 代码归因写入 Git 原生数据结构，并提供 blame、diff、stats、search、prompt 查询和团队同步能力。

项目遵循 Git AI Standard v3.0.0，以 `refs/notes/ai` 中的 authorship log 作为提交级 AI 归因事实来源。

### 5.2 源码模块划分

| 模块 | 路径 | 责任 |
|------|------|------|
| 入口 | `src/main.rs` | 根据 binary name 分发到 `git` 代理模式或 `git-ai` CLI 模式 |
| 命令层 | `src/commands/` | `git-ai` 子命令、Git proxy、Git hook 处理、安装和调试命令 |
| Git 抽象 | `src/git/` | repository 发现、Git CLI 包装、refs、status、repo state、rewrite log、authorship sync |
| 归因核心 | `src/authorship/` | checkpoint、working log、post commit、authorship log、stats、blame/range 归因、历史改写 |
| Metrics | `src/metrics/` | 事件定义、position encoded payload、本地 metrics db |
| API client | `src/api/` | 调用后端 metrics、CAS、authorship notes、bundle 等 API |
| Auth | `src/auth/` | OAuth device flow、凭证状态、系统 keyring/文件 fallback |
| Daemon | `src/daemon/` | async mode、control API、trace normalizer、actor/reducer、telemetry worker |
| Observability | `src/observability/` | tracing、日志、错误、性能和 telemetry flush |
| MDM/安装 | `src/mdm/` | Git shim、agent、IDE/Git client 安装支持 |
| Agent support | `agent-support/` | VS Code、IntelliJ、OpenCode、Pi 等集成代码 |
| 规范和文档 | `specs/`, `docs/` | Git AI Standard、设计记录、迁移计划 |

### 5.3 运行模式

`src/main.rs` 根据可执行文件名分发：

- 当可执行名为 `git` 时，进入 Git proxy 模式，代理真实 Git 命令并按子命令执行 pre/post hook。
- 当可执行名为 `git-ai` 时，提供 direct CLI，例如 `checkpoint`、`blame`、`diff`、`status`、`search`、`sync` 等。
- debug 构建下，如果 `GIT_AI=git`，即使可执行名不是 `git` 也强制进入 Git proxy 模式，便于集成测试。
- 旧 Git core hook binary name 只提示迁移，当前 core hooks 功能已 sunset。

```text
process argv[0]
    |
    +-- git-ai / git-ai.exe -> commands::git_ai_handlers::handle_git_ai()
    |
    +-- git hook binary    -> print deprecation guidance
    |
    +-- otherwise          -> commands::git_handlers::handle_git()
```

### 5.4 Git proxy 与 hook 架构

Git proxy 模式由 `src/commands/git_handlers.rs` 实现。处理流程：

1. 解析 Git CLI 参数，识别 global args、command、command args。
2. 处理 shell completion、help、read-only、skip-hooks、clone/init 等特殊路径。
3. 查找当前 repository，并根据 `Config::is_allowed_repository()` 判断是否启用 hooks。
4. 对需要追踪的命令运行 pre-command hooks。
5. 调用真实 Git binary。
6. 对成功或可处理的命令运行 post-command hooks。
7. 保留真实 Git exit status。

核心 hook 模块：

| Hook 模块 | Git 命令/场景 | 责任 |
|-----------|----------------|------|
| `commit_hooks` | `git commit` | pre 阶段捕获 virtual attribution，post 阶段生成 authorship note 和 stats |
| `rebase_hooks` | `git rebase` | 记录 original head/onto，post 阶段重写 rebased commits 的 authorship |
| `cherry_pick_hooks` | `git cherry-pick` | 将源提交归因复制/适配到新提交 |
| `reset_hooks` | `git reset` | reset 后重建 working log 或清理状态 |
| `stash_hooks` | `git stash/pop` | 在 stash 流程中保留未提交 AI 归因 |
| `merge_hooks` | `git merge` | merge 相关归因处理 |
| `checkout_hooks` / `switch_hooks` | 切换工作区 | 处理工作区状态切换 |
| `fetch_hooks` / `push_hooks` | 远端同步 | fetch/push authorship notes |
| `clone_hooks` | `git clone` | clone 后同步和初始化 |
| `update_ref_hooks` / `plumbing_rewrite_hooks` | refs 变化 | 捕获底层历史改写事件 |

Unix 下 proxy 会安装信号转发处理，将 SIGTERM、SIGINT、SIGHUP、SIGQUIT 转发给真实 Git 子进程组，保持 Git 行为透明。

### 5.5 CLI 命令设计

`src/commands/git_ai_handlers.rs` 是 `git-ai` direct CLI 分发器。主要命令：

| 命令 | 责任 |
|------|------|
| `checkpoint` | Agent/IDE 调用，用于记录文件变更和归因来源 |
| `stats` | 输出 commit 或 range 的 AI/人工/混合统计 |
| `blame` | 类 `git blame` 输出每行 AI 归因 |
| `diff` | 归因感知 diff |
| `status` / `show` / `log` | 查看仓库归因状态和提交信息 |
| `fetch-notes` / `push-authorship-notes` | 与远端/REST notes store 同步 authorship notes |
| `flush-cas` / `flush-logs` / `flush-metrics-db` | 手动 flush 本地 CAS、日志和 metrics |
| `login` / `logout` / `whoami` / `exchange-nonce` | OAuth 登录和身份管理 |
| `share` / `sync-prompts` / `show-prompt` / `prompts` / `search` / `continue` | Prompt/session 查询、同步、分享和继续会话 |
| `daemon` / `bg` / `d` | 管理后台 daemon |
| `install` / `install-hooks` / `uninstall-hooks` | 安装或卸载 Git/agent 集成 |
| `ci` | CI 环境下的归因检查和集成 |

命令层只做参数解析、运行模式判断、错误输出和状态码处理，复杂逻辑下沉到 `authorship`、`git`、`api`、`daemon` 等模块。

### 5.6 归因数据模型

#### 5.6.1 Checkpoint 类型

`git-ai checkpoint` 是归因入口。当前主要 checkpoint 类型：

| 类型 | 语义 |
|------|------|
| `human` | legacy 名称，当前表示 untracked/未知来源变更，常用于 AI agent 的 pre-edit snapshot |
| `known_human` | 明确的人类编辑，由 IDE/editor 集成触发 |
| `ai_agent` | 明确的 AI 编辑，由 Agent preset 的 post-edit hook 触发 |
| mock variants | 测试用，例如 `mock_ai`、`mock_known_human` |

Agent preset 会根据不同工具的 hook payload 抽取文件路径、会话 ID、模型、prompt/transcript metadata，然后调用 checkpoint 逻辑。

#### 5.6.2 Working Log

Checkpoint 结果写入 `.git/ai/working_logs/<base_commit>/`。Working log 记录：

- base commit。
- 文件路径。
- 行级归因范围。
- AI/human/untracked 类型。
- Agent ID、tool、model、session/prompt metadata。

Working log 是 commit 前的临时归因状态，post-commit hook 会把它转换为 commit 级 authorship log。

#### 5.6.3 Authorship Log

Commit 后生成的 `AuthorshipLog` 存储为 Git Note：

- ref namespace: `refs/notes/ai`。
- schema version: `authorship/3.0.0`。
- attestation section: 文件路径 -> prompt hash -> 行号范围。
- metadata section: prompt hash -> agent、model、human author、messages、accepted lines、total additions/deletions 等。

Authorship log 设计要点：

- 不修改 commit 对象和提交历史。
- 只记录 AI 归因行，不需要列出纯人工行。
- 行号以 commit 当时文件内容为准，1-based。
- prompt hash 与 metadata 中 prompts 键对应。
- metadata 支持链接或携带 prompt/session 摘要，完整内容可通过 CAS/远端 prompt store 扩展。

### 5.7 归因计算流程

核心链路：

```text
Agent edit hooks
    -> git-ai checkpoint
    -> .git/ai/working_logs/<base_commit>/
    -> git commit post hook
    -> AuthorshipLog
    -> Git Note refs/notes/ai
    -> metrics / notes sync to backend
```

关键模块：

- `authorship/attribution_tracker.rs`: 根据文件前后内容计算变更，并维护行级 attribution。
- `authorship/working_log.rs`: working log 数据结构与持久化。
- `authorship/post_commit.rs`: commit 后读取 working log，生成 authorship log。
- `authorship/authorship_log_serialization.rs`: authorship log 序列化/反序列化。
- `authorship/stats.rs`: 根据 authorship log 和 Git diff 计算统计。
- `authorship/diff_ai_accepted.rs`: 计算 AI accepted 相关指标。
- `authorship/virtual_attribution.rs`: 用于 blame/range/rewrite 场景的虚拟归因。

`git-ai` 不通过猜测识别 AI 代码，而是由 Agent checkpoint 明确记录变更来源。

### 5.8 历史改写与归因保持

Git 历史改写会改变 commit SHA 和文件行号，因此 `git-ai` 需要在下列操作后保持归因：

- rebase。
- cherry-pick。
- reset。
- merge / squash merge。
- stash / pop。
- commit amend。
- plumbing ref updates。

设计机制：

1. pre hook 记录操作前 HEAD、ref、working tree、virtual attribution 或 rewrite 上下文。
2. 真实 Git 命令执行。
3. post hook 根据 rewrite log、commit ancestry、文件最终内容和原始 authorship notes 重算或迁移归因。
4. 生成新的 authorship note 或更新 working log。

关键模块：

- `git/rewrite_log.rs`: 记录历史改写事件。
- `authorship/rebase_authorship.rs`: rebase/cherry-pick/amend/merge 等场景的归因重写。
- `authorship/range_authorship.rs`: 范围提交归因统计和 squash-like in-memory authorship log。
- `authorship/duplicate_parent_ai.rs`: 处理父提交重复 AI note 等边界情况。

### 5.9 Blame、Diff、Stats 查询

查询命令使用 Git 原生数据和 authorship notes：

- `git-ai blame`: 兼容常见 `git blame` flags，同时把行作者替换或增强为 AI agent/model/session 信息。
- `git-ai diff`: 基于 diff 结果显示 AI 归因变化。
- `git-ai stats`: 对单 commit 或 commit range 汇总 human additions、mixed additions、AI additions、AI accepted、total AI additions/deletions、time waiting for AI 等。
- `git-ai search` / `show-prompt`: 通过本地 internal DB、prompt metadata 或远端同步数据检索 session/prompt。

统计不会把“像 AI 写的代码”作为依据，只使用 authorship log 与 checkpoint 产生的数据。

### 5.10 Metrics 与本地存储

Metrics 子系统位于 `src/metrics/`：

- `events.rs`: 定义 committed、agent usage、install hooks、checkpoint 等事件位置编码。
- `attrs.rs`: 定义通用 attributes 的 position mapping。
- `pos_encoded.rs`: position encoded payload 编解码。
- `db.rs`: 本地 metrics SQLite 存储。
- `types.rs`: batch 和事件类型。

Metrics 通过本地数据库先落盘，再由 flush 命令或 daemon telemetry worker 上传：

```text
git-ai command/checkpoint/commit
    -> metrics event
    -> local metrics db
    -> flush_metrics_db or daemon telemetry worker
    -> ApiClient.upload_metrics()
    -> backend /worker/metrics/upload
```

`upload_metrics_with_retry()` 对非 200 响应进行一次延迟重试；200 响应中的 partial errors 只记录，不重试。

### 5.11 API、CAS 与 Auth

`src/api/client.rs` 统一构建 HTTP 请求：

- base URL 来自 config/env/default。
- API Key 通过 `X-API-Key` 发送。
- Bearer token 通过 OAuth credential 状态提供。
- `post_json`、`get_json` 等方法构造 Worker API 请求。

API 模块：

| 模块 | 责任 |
|------|------|
| `api/metrics.rs` | metrics batch 上传和重试 |
| `api/cas.rs` | CAS 对象上传、按 hash 读取 |
| `api/authorship_notes.rs` | notes list、batch get、push、rewrite |
| `api/bundle.rs` | bundle 上传/创建能力 |
| `api/types.rs` | Worker API 请求/响应结构 |

Auth 模块：

- `auth/client.rs`: OAuth device code、token、refresh token 请求。
- `auth/credentials.rs`: 凭证加载、刷新、清理。
- `auth/credential_backend.rs`: keyring backend 与 file backend。

Release 构建中 OAuth base URL 要求 HTTPS；debug 构建可用于本地 HTTP 开发。

### 5.12 Daemon 与 Async Mode

`git-ai` 同时支持传统 wrapper mode 和 async daemon mode。

Async mode 目标：

- Git wrapper 对真实 Git 命令保持低延迟 passthrough。
- wrapper 只捕获 pre/post repo state 和 trace2 信息。
- 后台 daemon 归一化 Git 命令事件、维护 repo family 状态、异步处理 checkpoint/telemetry。

主要模块：

| 模块 | 责任 |
|------|------|
| `daemon/control_api.rs` | CLI 和 daemon 的控制请求/响应 |
| `daemon/telemetry_handle.rs` | wrapper/CLI 连接 daemon telemetry/control socket |
| `daemon/trace_normalizer.rs` | 将 Git trace/wrapper state 转换成 NormalizedCommand |
| `daemon/coordinator.rs` | 按 command scope 路由到 global actor 或 family actor |
| `daemon/global_actor.rs` | 处理全局命令状态 |
| `daemon/family_actor.rs` | 按 repo family 串行处理状态更新 |
| `daemon/reducer.rs` | 将 NormalizedCommand 应用到 state |
| `daemon/analyzers/*` | workspace/history/transport/generic 命令分析 |
| `daemon/telemetry_worker.rs` | 每 3 秒批量 flush telemetry、metrics、CAS |

Daemon 的 actor 模型让同一 repo family 的命令串行化，降低并发 Git 操作导致的状态竞争。

### 5.17 详细架构分层

`git-ai` 的运行时可划分为 6 个层次。每层只暴露有限接口，避免命令层直接操作归因细节。

```text
git / git-ai process
        |
        v
commands
  - git_handlers: Git proxy
  - git_ai_handlers: direct CLI
  - checkpoint_agent: tool-specific preset parsing
        |
        +---------------------+---------------------+
        |                     |                     |
        v                     v                     v
authorship              git storage/refs        daemon async mode
  - checkpoint          - repo discovery        - trace normalizer
  - working log         - status/diff/refs      - coordinator
  - post commit         - notes/rewrite log     - family/global actors
  - rewrite/blame       - sync authorship       - reducers/analyzers
        |                     |                     |
        +----------+----------+----------+----------+
                   |
                   v
local persistence and remote services
  - .git/ai/*
  - local SQLite metrics/internal db
  - refs/notes/ai
  - Worker API / CAS / OAuth
```

关键边界：

| 边界 | 设计约束 |
|------|----------|
| `commands` -> `authorship` | 命令层传入 repo、参数、agent payload 和 author，不直接构造 authorship note |
| `authorship` -> `git` | 归因模块通过 Git 抽象读写 refs、diff、blame、notes，生产路径优先调用 Git CLI |
| `authorship` -> `api` | post-commit 和 push hook 只触发非阻塞或可降级上传，不能让 CAS/prompt 失败破坏 Git commit |
| `daemon` -> `authorship` | daemon 通过 captured checkpoint、post-command normalized state 和 reducer 结果调用归因能力 |
| `api/auth` -> `config` | API base URL、API key、OAuth token 和 prompt storage 由 `Config::fresh()` 或 `Config::get()` 统一解析 |

### 5.18 本地持久化布局

每个仓库使用 `.git/ai/` 作为客户端私有状态目录。该目录不属于工作区文件，不进入业务提交。

```text
.git/ai/
  working_logs/
    <base_commit>/
      checkpoints.jsonl
      checkpoints.lock
      INITIAL
      blobs/<sha256>
    old-<base_commit>/
      .archived_at
      checkpoints.jsonl
      INITIAL
  rewrite_log
  pending_rebase_pick.json
  logs/
```

主要文件语义：

| 文件/目录 | 语义 |
|-----------|------|
| `working_logs/<base_commit>/checkpoints.jsonl` | commit 前 checkpoint 追加日志，每行一个 `Checkpoint` JSON |
| `working_logs/<base_commit>/INITIAL` | 当前 base 下未提交但已有归因的初始行归因和 prompt map |
| `working_logs/<base_commit>/blobs/<sha256>` | checkpoint 或 INITIAL 关联的文件内容快照 |
| `working_logs/old-<base_commit>/` | commit 后归档的旧 working log，release 构建按保留期清理 |
| `rewrite_log` | rebase、amend、cherry-pick、reset 等历史改写事件 JSONL |
| `pending_rebase_pick.json` | rebase pick 中间状态，用于把源提交 note 映射到新提交 |
| `logs/` | 本地观测日志、Sentry/telemetry 待发送事件 |

`PersistedWorkingLog` 负责读写这些文件。它会把绝对路径归一化为仓库相对 POSIX 路径，读取文件内容时优先使用 `dirty_files` 快照，其次读取工作区文件。这样 async mode 或 captured checkpoint 可以基于捕获时刻的内容重放，而不是依赖稍后可能已变化的工作区状态。

`checkpoints.jsonl` 的追加不是简单 append：`append_checkpoint()` 会先读取已有 checkpoint，必要时移除可重新抓取的 transcript，追加新 checkpoint，再对同一文件的旧 checkpoint 裁剪 char-level attribution，只保留最新文件版本的高精度归因，控制本地状态大小。

### 5.19 Checkpoint 数据契约

Checkpoint 是 commit 前的归因事实记录，定义在 `authorship/working_log.rs`。

```text
Checkpoint
  kind: human | ai_agent | ai_tab
  diff: string
  author: git author / tool author
  entries: WorkingLogEntry[]
  timestamp: unix seconds
  transcript?: AiTranscript
  agent_id?: { tool, id, model }
  agent_metadata?: map<string,string>
  line_stats: { additions, deletions, additions_sloc, deletions_sloc }
  api_version: checkpoint/1.0.0
  git_ai_version?: string

WorkingLogEntry
  file: repo-relative POSIX path
  blob_sha: sha256 of file content at checkpoint
  attributions: char/range attribution records
  line_attributions: final line attribution records
```

Checkpoint kind 语义：

| kind | 是否 AI | 典型来源 | 说明 |
|------|---------|----------|------|
| `human` | 否 | pre-edit snapshot、未知来源变更、legacy `known_human` 映射 | 用于划定 AI 编辑前基线，或明确记录人工覆盖 |
| `ai_agent` | 是 | Agent post-edit hook | 常规 AI 会话输出 |
| `ai_tab` | 是 | tab completion 类工具 | 用于区分短补全类 AI 编辑 |

`agent_id` 不是展示名称，而是 prompt/session hash 的输入。`generate_short_hash(agent_id.id, agent_id.tool)` 生成 authorship note 中的 prompt hash；attestation section 中出现的每个 hash 必须能在 metadata `prompts` 中找到对应 `PromptRecord`。

### 5.20 Checkpoint 生命周期

`git-ai checkpoint` 的核心流程由 `commands/checkpoint.rs` 实现。

```text
agent/editor hook
    |
    v
parse preset payload
    |
    v
resolve_live_checkpoint_execution()
    - resolve repository and base commit
    - resolve explicit paths / dirty files / pathspecs
    - apply ignore rules and repo boundary checks
    - skip unmerged or external paths
    |
    v
execute_resolved_checkpoint()
    - open working log for base commit
    - read previous checkpoints and INITIAL
    - save current file states to blobs
    - calculate checkpoint entries and line stats
    - attach transcript / agent_id / metadata
    - upsert prompt record to internal db best-effort
    - append checkpoint to checkpoints.jsonl
    - enqueue checkpoint metrics
```

输入解析规则：

| 输入 | 处理规则 |
|------|----------|
| Agent preset | `checkpoint_agent/*` 把不同工具 payload 统一为 kind、author、edited paths、will-edit paths、transcript metadata |
| 显式文件路径 | 归一化为仓库内 POSIX 相对路径；仓库外路径过滤；冲突状态路径跳过 |
| dirty files | async/captured checkpoint 可提供内容快照，避免执行时再次读工作区 |
| base commit override | 用于 daemon 或历史重放；需要显式 snapshot 来保证重放内容一致 |
| ignore patterns | 按 `.gitignore`/配置忽略规则过滤无需归因的文件 |

跳过条件：

- pre-commit 阶段没有 AI checkpoint、没有 INITIAL 归因、也没有显式 AI context。
- 文件没有内容变化，且没有需要迁移的 INITIAL attribution。
- 文件处于 unmerged/conflict 状态。
- 显式路径不在仓库工作区内。
- captured checkpoint manifest 与当前 repo workdir 不匹配。

失败策略：

| 失败点 | 策略 |
|--------|------|
| prompt internal DB upsert 失败 | 记录错误，不阻断 checkpoint |
| checkpoint path 部分无效 | 过滤无效路径，继续处理有效文件 |
| checkpoint api_version 不兼容 | 读取时静默跳过该 checkpoint |
| base override 缺少必要 snapshot | 返回错误，避免错误归因 |
| metrics 记录失败 | 不阻断用户 Git 工作流 |

### 5.21 Captured Checkpoint 与 async 重放

在 async mode 或 shell tool pre/post hook 场景中，checkpoint 可以先捕获后应用。

```text
prepare_captured_checkpoint()
    -> create capture_id
    -> write manifest.json
    -> persist target file blobs
    -> return capture handle

apply_captured_checkpoint(capture_id)
    -> read manifest
    -> validate repo workdir
    -> load captured blobs as dirty_files
    -> execute checkpoint with base_commit override
```

`PreparedCheckpointManifest` 保存 base commit、repo workdir、checkpoint kind、author、目标文件、捕获时间和 agent result。pre-hook capture 使用 `will_edit_filepaths` 记录 AI 修改前状态；post-hook capture 使用 `edited_filepaths` 记录 AI 修改后状态。该设计解决两类问题：

- Git wrapper 或 agent hook 需要快速返回，不能在热路径做完整归因计算。
- 工作区内容可能在后台处理前继续变化，必须用捕获时的 blob 保证归因输入稳定。

### 5.22 Post-Commit 归因生成流程

`authorship/post_commit.rs::post_commit_with_final_state()` 将 working log 转换为 commit 级 Git note。

```text
git commit succeeds
    |
    v
post_commit_with_final_state(repo, base_commit, commit_sha, human_author)
    |
    +-- open working_logs/<base_commit>
    +-- lock and refresh checkpoints
    +-- refresh prompt metadata from tool-specific transcript stores
    +-- batch upsert prompts into local internal db
    +-- build pathspecs from AI checkpoint entries and INITIAL
    +-- build VirtualAttributions from working log or final-state snapshot
    +-- convert virtual attribution to AuthorshipLog
    +-- set metadata.base_commit_sha = commit_sha
    +-- apply prompt storage mode
    +-- serialize authorship log
    +-- git notes --ref=ai add commit_sha
    +-- compute stats and record committed metrics
    +-- write INITIAL for uncommitted carryover
    +-- archive old working log
```

关键设计点：

| 阶段 | 设计说明 |
|------|----------|
| checkpoint refresh | post-commit 前重新读取 Claude/Cursor/Copilot 等外部 transcript，补齐 checkpoint 中省略的 messages |
| pathspec selection | 只针对 AI-relevant checkpoint、INITIAL 和 whitespace-only uncheckpointed changes 构建 pathspec，降低 diff/blame 成本 |
| virtual attribution | 将 commit 前 working log、文件最终内容、INITIAL 和 blame 结果合成为可写入 note 的虚拟行归因 |
| prompt storage | 按 `local`、`notes`、`default` 决定 messages 留在本地、进入 note 或上传 CAS |
| stats 计算 | merge commit 或预计成本过高时可跳过详细 stats，避免拖慢 commit |
| carryover INITIAL | 对 commit 后仍未提交的 AI 归因写入新 base 的 `INITIAL`，保证后续 commit 继续追踪 |

Prompt 存储模式：

| 模式 | 行为 | 使用场景 |
|------|------|----------|
| `local` | note 中移除 messages，仅保留 prompt record 元数据；完整 prompt 留在本地 internal DB | 默认隐私优先或仓库不允许写入 prompt |
| `notes` | secret redaction 后把 messages 写入 Git note metadata | 团队希望 prompt 随 Git notes 同步 |
| `default` | 登录/API 可用时上传 messages 到 CAS，note 中写 `messages_url` 或去除 messages；不可上传时降级为本地策略 | 推荐云端同步模式 |

### 5.23 Authorship Log 格式与语义

`AuthorshipLog` 由两段组成，中间用精确的 `---` 分隔。第一段是 attestation，第二段是 JSON metadata。

```text
src/file.rs
  c9883b05a2487d6d 1-10,15
  8e3c1f0a12b34567 20-25
"docs/file with spaces.md"
  c9883b05a2487d6d 3
---
{
  "schema_version": "authorship/3.0.0",
  "git_ai_version": "development",
  "base_commit_sha": "<commit_sha>",
  "prompts": {
    "c9883b05a2487d6d": {
      "agent_id": {
        "tool": "cursor",
        "id": "session_123",
        "model": "claude-3-sonnet"
      },
      "human_author": "Alice <alice@example.com>",
      "messages": [],
      "total_additions": 25,
      "total_deletions": 3,
      "accepted_lines": 20,
      "overriden_lines": 0,
      "messages_url": "https://.../cas/<hash>"
    }
  }
}
```

格式约束：

- Git Notes namespace 固定为 `refs/notes/ai`。
- `schema_version` 固定为 `authorship/3.0.0`。
- 文件路径含空格或特殊字符时使用引号序列化。
- 行号为 commit 文件内容中的 1-based 行号。
- line range 支持单行和连续区间压缩。
- attestation 中每个 hash 必须存在于 `metadata.prompts`。
- `overriden_lines` 是 v3.0.0 已发布字段名，虽然拼写有误但在该版本中保持兼容。

后端消费 authorship note 时必须把 note 当作不可变事实输入，不根据 prompt 文本或代码内容重新推断 AI 归因。

### 5.24 历史改写状态机

历史改写会同时影响 commit SHA、parent、文件行号和 note 指向。`git-ai` 使用 pre/post hook、rewrite log 和 VirtualAttributions 组合处理。

```text
Idle
  |
  | pre hook captures old HEAD/ref/worktree/note context
  v
RewritePrepared
  |
  | real git command executes
  +-- failure --> AbortOrNoop
  |
  v
RewriteApplied
  |
  | post hook resolves old->new commit mapping
  v
AuthorshipRemap
  |
  +-- source note exists -----> remap note ranges/base_commit_sha
  +-- working log exists -----> migrate INITIAL/checkpoints
  +-- no AI context ----------> no-op
  |
  v
NotesWritten
  |
  | cleanup transient state
  v
Idle
```

场景策略：

| Git 操作 | 归因策略 |
|----------|----------|
| `commit --amend` | 根据新 commit 文件内容重算 note，`base_commit_sha` 指向 amended commit 或新 parent 语义要求的提交 |
| `rebase` | pre 阶段记录 original head/onto；post 阶段使用 commit mapping、pending pick 和源 note 重写新提交 note |
| `cherry-pick` | 将源 commit note 映射到新 commit，必要时按最终内容裁剪行号 |
| `reset` | 将已提交 note 或 working log 转成新 base 下的 INITIAL，保留未提交归因 |
| `stash` / `stash pop` | stash 时把当前 working log 保存到 `refs/notes/ai-stash`，pop 后恢复 VirtualAttributions |
| `checkout --merge` / `switch --merge` | 切换前捕获 VirtualAttributions，切换后按文件最终内容恢复 working log |
| `pull --rebase --autostash` | fetch hook 捕获未提交 VirtualAttributions，rebase/stash 完成后迁移 |
| plumbing ref update | 使用 `update_ref_hooks` 和 `plumbing_rewrite_hooks` 捕获底层 refs 变化 |

`rewrite_log` 是可恢复的中间事实。即使命令链中断，后续 hook 也能读取历史事件，判断是否需要补写 note 或迁移 INITIAL。

### 5.25 Git Proxy 执行细节

Git proxy 的目标是透明：真实 Git 行为和 exit status 必须优先保留。

```text
handle_git()
    -> parse global args and command
    -> resolve aliases
    -> classify command
    -> if async_mode and command eligible:
           capture pre state
           run real git
           capture post state
           send wrapper event to daemon
           return real git status
       else:
           run pre hooks
           run real git with signal forwarding
           run post hooks
           return real git status
```

命令分类：

| 分类 | 处理方式 |
|------|----------|
| read-only 命令 | 默认 passthrough，不触发昂贵 hooks |
| repo-creating 命令 | `clone`/`init` 有专用初始化流程，不要求当前 repo 存在 |
| mutating workspace 命令 | 运行 workspace 类 hooks 或 daemon analyzer |
| history rewrite 命令 | 运行 pre/post rewrite hooks，写 `rewrite_log` |
| transport 命令 | `fetch`/`push` 同步 authorship notes 和 CAS/metrics |
| skip-hooks 场景 | 保留 Git 行为，跳过归因处理 |

Unix 环境下 proxy 对真实 Git 子进程组做信号转发，避免 Ctrl-C、终止信号只杀 wrapper 不杀 Git。所有 post hook 必须以真实 Git exit status 为前置条件，不能把失败 Git 命令误判为成功归因事件。

### 5.26 Daemon Async Mode 详细设计

Async mode 将 wrapper 热路径和归因计算拆开。

```text
Git wrapper
  -> capture pre repo state
  -> run real git
  -> capture post repo state / trace2
  -> send WrapperCommand to daemon socket
  -> return

Daemon
  -> trace_normalizer builds NormalizedCommand
  -> coordinator routes by command scope
  -> family_actor serializes repo-family state changes
  -> reducer applies command to FamilyState
  -> analyzers emit effects
  -> effects call checkpoint/post_commit/rewrite/sync
  -> telemetry_worker flushes metrics/logs/CAS
```

核心状态：

| 组件 | 状态/职责 |
|------|-----------|
| `NormalizedCommand` | 归一化后的命令名、参数、pre/post refs、worktree state、trace2 信息 |
| `Coordinator` | 根据命令作用域路由到 global actor 或 repo family actor |
| `FamilyActor` | 维护同一 repo family 的 refs、worktrees、last_error、applied_seq、watermarks |
| `GlobalActor` | 处理不归属单个 repo family 的全局命令 |
| `Reducer` | 把 normalized command 应用到 actor state，输出需要执行的副作用 |
| `TelemetryWorker` | 每 3 秒批量 flush logs、metrics、CAS，阻塞 HTTP 操作放入 blocking 线程 |

Watermark 设计用于测试和控制面：wrapper 或 CLI 可以等待 daemon 已应用到某个 sequence，避免异步处理导致状态读取不一致。repo family 串行化保证同一仓库的连续 Git 操作按观察顺序处理；不同仓库 family 可并发处理。

Async mode 不适用所有命令。read-only 和 repo-creating 命令可直接 passthrough；需要即时返回结果的命令仍走同步路径或等待 daemon control API。

### 5.27 Metrics 事件契约

客户端 metrics 使用 position encoded payload 降低上传体积，事件先写本地 SQLite，再批量上传到 `/worker/metrics/upload`。

| event id | 客户端事件 | 重要 values | 后端结构化表 |
|----------|------------|-------------|--------------|
| `1` | committed | human additions、git diff added/deleted、tool/model pairs、mixed additions、AI additions、AI accepted、total AI additions/deletions、time waiting for AI、first checkpoint ts、commit subject/body | `metrics_events_committed` |
| `2` | agent usage | tool、model、prompt/session、作者和仓库属性 | `metrics_events_agent_usage` |
| `3` | install hooks | tool id、安装状态、message、git-ai version | `metrics_events_install_hooks` |
| `4` | checkpoint | checkpoint kind、file path、lines added/deleted、SLOC added/deleted、tool/model/prompt | `metrics_events_checkpoint` |

通用 attributes 包括 git-ai version、repo URL、author、commit SHA、base commit SHA、branch、tool、model、prompt id、external prompt id 和 custom attributes。后端解析 raw payload 时必须按 position mapping 解码，不能按 JSON 字段名猜测。

上传策略：

- 本地命令/checkpoint/commit 只负责写 local metrics db。
- `flush_metrics_db`、push hook 或 daemon telemetry worker 发起批量上传。
- `upload_metrics_with_retry()` 对非 200 响应延迟 60 秒重试一次。
- HTTP 200 但包含 partial errors 时记录错误，不重试已接受 batch。

### 5.28 REST Notes Store 与 Git Notes 同步

`git-ai` 支持两条 authorship notes 同步路径：

1. Git 原生同步：fetch/push `refs/notes/ai`。
2. REST Notes Store：调用 Python 后端 `/worker/authorship_notes/*`。

```text
local refs/notes/ai
    -> list local notes
    -> normalize repo remote URL
    -> compare REST change_seq/content_hash
    -> batch push missing or changed notes
    -> batch get remote missing notes
    -> write notes locally with git notes
```

REST 数据契约：

| 字段 | 语义 |
|------|------|
| `repo_url` | 归一化后的仓库 URL，作为同步命名空间 |
| `commit_sha` | note 归属 commit |
| `note_content` | Git AI Standard v3.0.0 authorship log 原文 |
| `content_hash` | note content hash，用于冲突/变化判断 |
| `change_seq` | 后端单调递增序号，用于增量 list |
| `commit_time` / `commit_date` | 用于按时间范围查询和统计 |
| `author_name` / `author_email` | note 记录者或 commit author 信息 |

同步冲突原则：

- 本地 `refs/notes/ai` 是用户仓库内的直接事实来源。
- REST store 是团队共享和后端分析索引，不应生成不符合标准的 note。
- 同一个 `repo_url + commit_sha` 使用 upsert，后端以 content hash 和 change_seq 暴露变化。
- 当前客户端存在 `authorship_notes/rewrite` 调用，后端路由尚未实现；该接口应补齐，或客户端避免依赖该路径。

### 5.29 配置、认证与隐私

配置读取层级：

```text
defaults
  -> ~/.git-ai/config.json
  -> environment GIT_AI_*
  -> test-only GIT_AI_TEST_CONFIG_PATCH
```

重要配置：

| 配置 | 说明 |
|------|------|
| `api_base_url` | Worker API/OAuth/CAS 的 base URL |
| `api_key` | 发送为 `X-API-Key` |
| `prompt_storage` | `default`、`notes`、`local` |
| `default_prompt_storage` | 不在 include list 内仓库的 fallback |
| `include_prompts_in_repositories` | 允许把 prompt 写入 notes/CAS 的仓库匹配规则 |
| `excluded_repositories` / allowed repositories | 控制哪些仓库启用 hooks |
| feature flags | 控制 async mode、rewrite stash、keyring 等能力 |

认证设计：

- API key 模式发送 `X-API-Key`，同时可带 `X-Author-Identity`。
- OAuth 模式发送 `Authorization: Bearer <access_token>`。
- access token 过期前 5 分钟刷新；进程内使用 mutex 避免同进程并发刷新风暴。
- 跨进程同时刷新被认为可接受，因为多个 refresh 结果都应为有效 token。
- credential backend 优先使用系统 keyring；不可用时回退文件 backend。文件 backend 在 Unix 设置 `0600`，Windows 使用 ACL/hidden 属性保护。

隐私设计：

- Release 构建中 prompt messages 默认不直接序列化到 note，除非配置要求。
- 写入 notes 或 CAS 前执行 secret redaction。
- API context 的 debug 输出对 token 和 API key 做 `[REDACTED]`。
- CAS/prompt 上传失败不影响 commit，避免用户为隐私或网络问题丢失 Git 操作。

### 5.30 性能、并发与恢复策略

性能边界：

| 场景 | 策略 |
|------|------|
| checkpoint 文件集合 | 使用显式 paths、dirty files、ignore rules 和 pathspec 限制计算范围 |
| 大文件/多 checkpoint | 旧 checkpoint 裁剪 char-level attribution，仅保留最新文件高精度状态 |
| post-commit stats | merge commit 或成本过高时跳过详细 stats，只保留 note 生成 |
| Git wrapper | read-only 命令 passthrough；async mode 把重计算移到 daemon |
| HTTP 上传 | metrics/CAS/logs 批量 flush，daemon 使用后台 worker |

并发控制：

- `checkpoints.lock` 保护 post-commit 期间的 checkpoint refresh 和写回。
- daemon 的 family actor 对同一 repo family 串行化命令应用。
- OAuth refresh 使用进程内 mutex。
- local internal db 初始化使用 `OnceLock`，schema 初始化用 upsert 处理并发初始化。
- Git notes 批量写入通过 Git refs 操作完成，避免手写 refs 文件。

恢复策略：

| 异常 | 恢复方式 |
|------|----------|
| post-commit 后旧 working log 需要排查 | 归档到 `old-<base_commit>`，release 构建保留 7 天 |
| rebase/cherry-pick 中断 | `rewrite_log` 和 `pending_rebase_pick.json` 保留上下文，后续 hook 可继续处理 |
| stash/pop 归因丢失风险 | 使用 `refs/notes/ai-stash` 暂存 stash 对应 authorship log |
| daemon 处理滞后 | control API/watermark 可等待处理到指定 sequence |
| REST/API 不可用 | Git note 本地仍存在；上传和同步可稍后 flush |
| prompt metadata 缺失 | post-commit 尝试 hydrate；失败时保留可用的 agent/session 元数据 |

## 6. 双项目集成设计

### 6.1 集成职责边界

| 责任 | `git-ai` 客户端 | Python 后端 |
|------|------------------|-------------|
| AI 变更捕获 | Agent checkpoint、Git proxy hooks | 不捕获本地编辑 |
| commit 级归因 | 生成 `refs/notes/ai` authorship log | 存储、查询、补偿和消费 note |
| metrics 产生 | 本地事件编码和落盘 | 接收 raw、异步解析、聚合 |
| prompt/session 内容 | 本地 internal DB、CAS payload | CAS 存储、搜索/分享数据承载 |
| 当前代码存量统计 | `git-ai blame/stats` 本地命令 | 服务端 clone + blame + authorship notes 聚合 |
| 历史改写修复 | 本地 hooks/rewrite | Codeup merge webhook 异步补偿 |
| 身份认证 | OAuth client、credential backend | OAuth/API Key 校验和 token 签发 |

### 6.2 Authorship Log 标准

后端按 Git AI Standard v3.0.0 消费 authorship log：

- Git Notes namespace: `refs/notes/ai`。
- Schema version: `authorship/3.0.0`。
- 内容由两段组成：
  - Attestation section：文件路径与 prompt hash 到行号区间的映射。
  - Metadata section：JSON，包含 `base_commit_sha`、`git_ai_version`、`prompts` 等。
- 行号是 commit 当时文件内容中的 1-based 行号。
- prompt hash 指向 metadata 中的 prompt record，包含 agent、model、session、accepted lines 等信息。

后端需要把 `note_content` 当作权威归因输入，不应自行改写格式，除 Codeup merge authorship 补偿流程外。

### 6.3 客户端调用的后端 API

`git-ai/src/api` 和 `git-ai/src/auth/client.rs` 当前会调用这些后端端点：

| 客户端能力 | 路径 | 当前状态与说明 |
|------------|------|----------------|
| metrics 上传 | `POST /worker/metrics/upload` | 上传本地 metrics batch |
| CAS 上传 | `POST /worker/cas/upload` | 上传 prompt/session 等内容对象 |
| CAS 读取 | `GET /worker/cas/?hashes=...` | 按 hash 批量读取对象 |
| OAuth device code | `POST /worker/oauth/device/code` | 获取 device/user code |
| OAuth token | `POST /worker/oauth/token` | device、refresh、install nonce token 交换 |
| notes list | `POST /worker/authorship_notes/list` | 按仓库列出 notes，支持增量 |
| notes batch get | `POST /worker/authorship_notes/batch` | 批量读取 commit notes |
| notes push | `POST /worker/authorship_notes/push` | 批量推送 notes |
| notes rewrite | `POST /worker/authorship_notes/rewrite` | `git-ai` 客户端已有调用；当前 Flask 路由未实现，应作为兼容缺口跟进 |
| releases | `GET /worker/releases/` | 查询发布 channel 和版本 |

认证支持：

- `X-API-Key`：与 `config.yaml` 的 `git_ai.api_key` 匹配。
- `Authorization: Bearer <jwt>`：使用 OAuth secret 校验。
- Debug 模式可放宽认证；生产环境应显式配置 API Key 或 OAuth。

## 7. 核心数据流

### 7.1 Metrics 采集与解析

```text
git-ai local metrics
    -> POST /worker/metrics/upload
    -> metrics_events_raw(extract=0)
    -> MetricsEventProcessorTask
    -> MetricsService.process_raw_event()
    -> metrics_events_committed/checkpoint/agent_usage/install_hooks
    -> stats repository/contributor/branch dimensions
    -> DailyAggregationTask
    -> stats_commit_daily
```

#### 7.1.1 上传阶段

`api/routes/git_ai_worker.py::metrics_upload()` 只保存原始 payload：

- 从请求读取 `v` 和 `events`。
- 写入 `metrics_events_raw`。
- 设置 `extract=0`，表示待解析。
- 返回 `raw_id`、`received_at` 和空/部分错误列表。

该设计使上传 API 的热路径保持较短，避免客户端等待复杂解析。

#### 7.1.2 解析阶段

`MetricsEventProcessorTask` 按批读取 pending raw records：

- 调用 `mark_raw_extracting()` 防止多进程重复处理。
- 调用 `MetricsService.process_raw_event()` 解析事件。
- 成功后标记 `extract=1`。
- 失败后标记失败并写入 `metrics_event_errors`。
- 同步仓库、贡献者、分支维度。

支持的 Git-AI event id：

| event id | 事件表 | 说明 |
|----------|--------|------|
| `1` | `metrics_events_committed` | commit 级 AI/人工/混合行数、工具模型、commit 信息 |
| `2` | `metrics_events_agent_usage` | Agent 使用事件 |
| `3` | `metrics_events_install_hooks` | hooks 安装事件 |
| `4` | `metrics_events_checkpoint` | checkpoint 文件变更事件 |

Committed event 使用 `gen_commited_uid()` 生成稳定 UID，并通过 upsert 保持幂等。

#### 7.1.3 每日聚合

`DailyAggregationTask` 从 committed events 聚合到 `stats_commit_daily`：

- 先执行 `consolidate_unknown_repositories()` 合并未知仓库维度。
- 按仓库读取 `last_daily_aggregation_id` 之后受影响的 commit date。
- 可通过 `require_authorship_notes` 要求 committed event 必须存在对应 authorship notes。
- 对每个受影响日期重新 upsert 日统计。
- 更新仓库的 `last_daily_aggregation_id` 游标。

### 7.2 Authorship Notes 同步与查询

```text
git-ai Git Note refs/notes/ai
    -> POST/PUT /worker/authorship_notes/*
    -> authorship_notes(repo_url, commit_sha)
    -> batch/list/search APIs
    -> blame stats / Codeup merge compensation / daily aggregation gate
```

后端同时提供两个 URL namespace：

- `/worker/authorship_notes`: 当前主要接口。
- `/worker/notes`: legacy 兼容接口。

主要操作：

| 操作 | 端点 | 说明 |
|------|------|------|
| 单条 upsert | `PUT /worker/authorship_notes` | 写入或更新 commit note |
| 单条获取 | `POST /worker/authorship_notes/get` | 根据 `repo_url + commit_sha` 获取 note |
| 批量获取 | `POST /worker/authorship_notes/batch` | 获取多个 commit notes，返回 missing |
| 批量推送 | `POST /worker/authorship_notes/push` | 批量 upsert notes |
| 增量列举 | `POST /worker/authorship_notes/list` | 支持 `since_commit_time`、`since_change_seq`、`limit` |
| 内容搜索 | `POST /worker/authorship_notes/search` | 在 note content 中搜索 |

`authorship_notes` 表使用 `repo_url + commit_sha` 唯一约束。`change_seq` 单调递增，用于客户端增量同步。

### 7.3 Git Blame 归因统计

```text
stats_repositories(repo_stats_flag=1)
    -> branch config / actual branches
    -> SSH key selection
    -> clone/fetch repo
    -> git blame --line-porcelain
    -> preload authorship_notes by commit
    -> parse attestation ranges
    -> stats_blame_repo / stats_blame_repo_contributor
```

`GitBlameStatsTask` 与 `BlameStatsService` 负责统计当前仓库代码存量中的 AI 行占比。处理步骤：

1. 从 `stats_repositories` 读取 `repo_stats_flag=1` 的仓库。
2. 根据仓库配置或默认配置选择 SSH Key。
3. clone/fetch 仓库到 `blame_stats.repo_cache_dir`。
4. 根据分支配置选择需要统计的分支。
5. 对文件执行 `git blame --line-porcelain`。
6. 批量预加载相关 commit 的 `authorship_notes`。
7. 解析 authorship log attestation ranges 判断每行是否 AI。
8. 聚合仓库级和贡献者级结果。
9. 写入 `stats_blame_repo`、`stats_blame_repo_contributor`。
10. 更新 `last_blame_commit_sha` 与 `last_stat_date`。

当前 ORM 结果表以仓库级和仓库贡献者级统计为准，不包含文件级结果表。

### 7.4 Codeup Merge Authorship 补偿

```text
Codeup merge webhook
    -> POST /webhook/codeup/merge
    -> CodeupWebhookService.enqueue_merge_event()
    -> codeup_merge_authorship_tasks
    -> CodeupMergeAuthorshipTask
    -> clone/fetch repo
    -> resolve merge source commits
    -> batch_get source/target notes
    -> MergeAuthorshipPolicy
    -> batch_push rewritten notes
```

该流程用于处理平台合并造成的 authorship notes 缺失或需要重算的场景。

关键设计点：

- Webhook 只入队，不在 HTTP 请求中执行 Git clone 和重算。
- `CodeupMergeAuthorshipDatabase.claim_next_task()` 控制任务领取。
- `max_attempts` 限制失败重试次数。
- 缺少 SSH Key 时释放任务等待后续重试。
- `CodeupGitService` 负责 fetch required refs、merge-base、rev-list、changed files 和 commit metadata。
- `MergeAuthorshipPolicy` 根据 merge 类型、源 notes、目标 note 和最终文件内容决定是否 upsert 新 note。

### 7.5 CAS、OAuth 与 Releases

CAS：

- `POST /worker/cas/upload` 接收对象数组并保存到 `cas_objects`。
- `GET /worker/cas/?hashes=...` 按 hash 批量读取。
- 单次读取限制最多 100 个 hash。

OAuth：

- `POST /worker/oauth/device/code` 生成 device code 和 user code。
- `POST /worker/oauth/token` 支持 device code、refresh token、install nonce 三种 grant。
- 客户端 release 构建要求 HTTPS；debug 构建可用于本地 HTTP 测试。

Releases：

- `GET /worker/releases/` 返回 `latest`、`next`、`enterprise-latest`、`enterprise-next` channel。
- 版本和 checksum 来自 `git_ai.releases` 配置。

### 7.6 辅助事件接收

系统还包含两类辅助数据入口：

- OTLP logs: `/v1/logs` 与 `/worker/otel/v1/logs`，用于接收 Claude Code 等工具的 invocation count。
- CX usage: `/api/v1/cx-aicode/events/batch` 与 `/api/v1/cx-aicode/codereview/events/batch`，用于记录命令使用和 code review 事件。

这些数据独立存储，不参与 Git-AI authorship log 的核心归因判定。

## 9. 调度器设计

### 9.1 任务注册

| `daily_aggregation` | `DailyAggregationTask` | 聚合每日 committed stats |

### 9.2 运行控制

`BaseTask.run()` 提供统一执行包装：

- 检查同 `job_id` 是否已有 running 记录。
- 创建 `task_running` 和 `task_executions`。
- 执行子类 `execute()`。
- 成功或失败后更新执行记录。
- 支持异步触发。

`scheduler.job_defaults` 当前支持：

- `coalesce`: 合并错过执行。
- `max_instances`: 同一 job 最大并发实例。
- `misfire_grace_time`: 错过执行宽限时间。

生产部署建议使用单 Gunicorn worker 或显式关闭多进程内的 scheduler，避免多个进程同时注册和触发后台任务。当前 Dockerfile 使用 `--workers 1`，符合该要求。

## 10. API 设计原则

### 10.1 响应风格

系统存在两类响应风格：

- Worker/authorship notes 风格：`{"ok": true, "data": ...}` 或 `{"ok": false, "error": ...}`。
- 业务查询风格：`{"success": true, "data": ...}` 或 `{"success": false, "error": ...}`。

新增 API 应优先复用所属模块的既有风格，避免同一路由组内混用。

### 10.2 认证

`core/middleware/auth.py::auth_required` 支持：

1. `X-API-Key`，匹配 `git_ai.api_key`。
2. `Authorization: Bearer <jwt>`，使用 `git_ai.oauth.secret_key` 验证。
3. `web.debug=true` 时允许跳过认证。

当前部分 Worker API 中认证装饰器被注释。生产环境应确认以下端点的认证策略：

- `/worker/metrics/upload`
- `/worker/cas/upload`
- `/worker/cas/`

Authorship notes API 已使用 `@auth_required`。

### 10.3 幂等与重试

- Metrics raw upload 是 append-only；解析阶段通过 raw `extract` 状态控制。
- Committed event 使用稳定 UID upsert。
- Authorship notes 使用 `repo_url + commit_sha` upsert。
- Codeup merge task 使用 `repo_url + merge_request_id + merge_commit_sha` 唯一约束。
- Scheduler 使用 `task_running` 防止同 job 并发。
- Git-AI 客户端 metrics 上传对非 200 响应进行重试；200 中的 partial validation errors 不重试。

## 11. 安全与隐私设计

### 11.1 密钥

- API Key 存放在 `git_ai.api_key` 或环境变量覆盖配置中。
- OAuth secret 应通过环境变量提供，不应使用默认值部署生产。
- SSH 私钥通过 `SshKeyService` 加密存储在 `stats_ssh_keys.private_key_encrypted`。
- Git clone 过程中私钥写入临时文件，使用后应清理。

### 11.2 数据敏感性

Authorship notes 和 CAS 对象可能包含 prompt、session metadata、工具调用输入等上下文信息。生产部署需要：

- 限制 Worker API 访问来源。
- 启用 HTTPS。
- 启用 API Key 或 OAuth。
- 控制数据库访问权限。
- 明确日志中不得输出完整 note content、token、私钥和敏感 payload。

### 11.3 Git 操作安全

Git clone/fetch/blame 的输入来自仓库配置、Webhook payload 和数据库任务。服务层应继续保持：

- repo URL 校验。
- ref、branch、commit SHA、file path 校验。
- Git 命令 timeout。
- 仓库缓存目录隔离。

## 12. 部署与运行

### 12.1 本地运行

```bash
pip install -r requirements.txt
python app.py
```

默认端口由 `config.yaml` 的 `web.port` 控制，当前为 `8888`。

### 12.2 生产运行

Dockerfile 当前使用 Python 3.11 slim，并安装 Git、SSH、数据库客户端依赖。生产启动命令：

```bash
gunicorn app:app --bind 0.0.0.0:5000 --workers 1 --timeout 120
```

单 worker 设计是为了避免 scheduler 在多进程中重复运行。

### 12.3 数据库初始化与迁移

SQL 脚本位于 `sql/`，包括：

- metrics schema。
- authorship notes 增量同步迁移。
- daily aggregation 游标迁移。
- blame repo/person 统计迁移。
- Codeup/CX/OTEL 相关迁移。

当前项目没有集中式迁移框架。上线时需要按环境记录已执行 SQL，避免重复或漏执行。

### 12.4 观测与运维

- `/health` 返回服务健康状态。
- 日志由 `core/config/logging.py` 初始化，支持主日志、错误日志、访问日志和滚动。
- Scheduler API 可查看任务状态和手动触发任务。
- `task_executions` 可用于追踪任务执行结果和失败原因。
- `metrics_event_errors` 可用于定位 metrics payload 兼容性问题。
- Codeup task 表记录 attempts、status、last_error 和 result_summary。

## 14. 关键设计决策

| 决策 | 说明 |
|------|------|
| 上传与解析解耦 | metrics upload 只写 raw，后台任务解析，降低客户端等待和 API 热路径复杂度 |
| Git-AI notes 为归因权威 | 后端不猜测 AI 代码，只消费 `refs/notes/ai` 和 metrics |
| `git-ai` 单二进制双角色 | 通过 binary name 区分 Git proxy 与 direct CLI，减少安装复杂度 |
| Checkpoint 而非检测 | Agent/IDE 明确报告变更来源，避免后验猜测 AI 代码 |
| Git Notes 承载归因 | 不改写 commit 对象，归因数据可随 Git ref 独立同步 |
| Daemon actor 串行 repo family | async mode 降低 wrapper 热路径延迟，同时降低同仓库状态竞争 |
| REST Notes Store 双前缀 | `/worker/authorship_notes` 为当前接口，`/worker/notes` 保持兼容 |
| 统计维度独立维护 | 仓库、贡献者、分支维度从 metrics 中同步，供统计查询复用 |
| Scheduler 使用数据库状态 | `task_running` 与 `task_executions` 提供并发控制和执行审计 |
| Codeup merge 异步补偿 | webhook 入队，后台 clone/fetch/重算，避免 HTTP 请求超时 |
| Blame 统计使用 SSH clone | 后端通过受控 SSH Key 访问仓库，按配置进行存量代码统计 |

## 15. 风险与后续改进

| 风险/缺口 | 建议 |
|-----------|------|
| 部分 Worker API 认证被注释 | 生产环境启用 `@auth_required` 或在网关层限制来源 |
| 无统一迁移框架 | 引入 Alembic 或维护环境级 migration ledger |
| Scheduler 与 Web 进程耦合 | 中长期拆分为独立 worker 进程 |
| Authorship notes 可能含敏感上下文 | 强化访问控制、日志脱敏、数据保留策略 |
| 大仓库 blame 成本高 | 增加按 commit 游标的增量统计、分支级缓存、任务超时和限流 |
| Codeup merge 依赖仓库可 clone | 提供 SSH Key 配置巡检和任务失败告警 |
| 统计口径多源并存 | 明确 committed metrics、authorship notes、blame stats 三类指标口径 |
| `authorship_notes/rewrite` 端点缺失 | 若继续使用当前 `git-ai` 客户端，应补齐后端 rewrite API 或调整客户端同步策略 |
| `git-ai` hook 场景复杂 | 对 rebase、stash、amend、merge、partial staging 增加端到端场景测试 |
| Async mode 与 wrapper mode 并存 | 明确默认模式、迁移策略和故障回退路径 |
| Prompt/session 数据敏感 | 客户端和后端都需要默认脱敏、最小上传和访问控制策略 |
