## 1. 项目背景与目标

### 1.1 项目背景

随着 AI 辅助编程工具的普及，代码仓库中 AI 生成代码的比例日益增加。Git-AI Metrics API 旨在为企业团队提供一套完整的代码统计和分析系统，用于追踪和分析 AI 代码在仓库中的占比、贡献者使用情况、趋势变化等关键指标。

### 1.2 项目目标

1. **数据采集**: 接收 Git-AI 客户端上传的 Metrics 事件数据
2. **数据存储**: 高效存储和处理大规模 Metrics 数据
3. **数据分析**: 提供多维度（时间、仓库、贡献者）的统计聚合
4. **代码归因**: 使用 Git blame 技术统计仓库中 AI 代码的实际占比
5. **Web 服务**: 提供 RESTful API 供前端系统调用
6. **定时任务**: 自动化的数据处理和统计任务

#### 3.1.4 并发安全设计

使用数据库状态锁防止任务并发执行：

```python
def trigger_job_with_execution(job_id, context):
    # 1. 检查是否有正在运行的任务
    running = scheduler_db.get_running_task_execution(job_id)

    # 2. 超时检测机制
    if running and is_expired(running):
        # 标记为失败，允许新的执行
        scheduler_db.update_task_execution_status(id, "failed")
        running = None

    # 3. 如果有运行且未超时，返回空，阻止触发
    if running:
        return None

    # 4. 创建新的执行记录
    execution_id = scheduler_db.create_task_execution(job_id)

    # 5. 执行任务
    task_instance.run(execution_id)

    return execution_id
```

#### 3.2.3 事件解析设计

```python
class MetricsService:
    def process_raw_event(raw_id, payload_json):
        """解析原始事件记录"""
        # 1. JSON 解析 (带错误处理)
        payload = json.loads(payload_json)
        events = payload.get("events", [])

        # 2. 逐个事件处理
        for event in events:
            event_id = event.get("e")  # 事件类型
            values = event.get("v")     # 事件值
            attrs = event.get("a")      # 事件属性

            # 3. 根据 event_id 路由到对应处理器
            if event_id == 1:
                self._process_committed(values, attrs, raw_id)
            elif event_id == 2:
                self._process_agent_usage(values, attrs, raw_id)
            # ... 其他事件类型

        # 4. 返回处理结果统计
        return {
            "success": True,
            "events_processed": count,
            "error_count": errors
        }

    def _get_string(arr, pos):
        """安全获取字符串值"""
        val = arr.get(pos)
        if val is not None and isinstance(val, str):
            return val
        # 处理布尔值等边缘情况
        if isinstance(val, bool):
            return "true" if val else "false"
        return None
```

### 4.2 表设计说明

#### 4.2.1 事件处理表设计策略

使用异步处理模式分离数据接收和处理：

| 表 | 用途 | 关键字段 |
|----|------|----------|
| `metrics_events_raw` | 原始数据接收 | `extract` 状态字段 |
| `metrics_events_committed` | Committed 事件结构化 | `repo_url`, `author`, `commit_sha` |
| `metrics_events_checkpoint` | Checkpoint 事件结构化 | `file_path`, `lines_added` |
| `metrics_event_errors` | 错误记录 | `event_index`, `error_message` |

**设计优势**：
1. 快速接收数据，不阻塞客户端
2. 批量处理提升性能
3. 错误隔离，单个事件失败不影响整体
4. 支持重试和错误回溯

## 12. 技术选型与设计决策

### 12.1 技术栈对比

| 组件 | 选型 | 替代方案 | 选择理由 |
|------|------|----------|----------|
| Web 框架 | Flask | FastAPI / Django | 轻量级，灵活，满足需求 |
| ORM | SQLAlchemy | Peewee / 直接 SQL | 功能强大，生态成熟 |
| 任务调度 | APScheduler | Celery / rq | 内置即可，无外部依赖 |
| 数据库 | SQLite | PostgreSQL / MySQL | 开发简单，支持 PG/MySQL |
| 加密 | Fernet | AES / RSA | 简单易用，对称加密 |
| 前端 | Vue 3 | React / Angular | 轻量，渐进增强 |

### 12.2 设计决策说明

#### 为什么使用异步处理 Metrics 数据？

1. **性能考虑**: 立即返回响应，不阻塞客户端
2. **可靠性**: 批量处理，失败不影响其他事件
3. **可扩展性**: 未来可独立为微服务处理
4. **解耦**: 数据接收和数据处理分离

#### 为什么使用 SQL 而非 NoSQL？

1. **数据结构**: Metrics 数据有清晰的关系结构
2. **查询需求**: 需要复杂的聚合和关联查询
3. **一致性**: 财务级别的数据完整性要求
4. **成熟度**: SQLite/PostgreSQL 稳定可靠

#### 为什么使用装饰器注册任务？

1. **声明式**: 代码即配置，一目了然
2. **类型安全**: 编译时检查
3. **易于扩展**: 新增任务无需修改注册逻辑
4. **配置覆盖**: 运行时动态调整
